# 怎样跑跨模型评测

当前状态：尚未调用多家模型，不能宣称已经验证跨模型稳定性。程序测试通过也不能替代这一步。外部模型名单、调用预算和账号由用户决定，脚本不会自行发请求。

1. 固定当前代码、依赖、资料版本和cases.yaml。按每例四柱运行paipan.py --chart，保存程序事实包；此处不需要生日。
2. 给每个模型相同的SKILL、按需references及同一个事实包。只含四柱的例不能要求模型造出真实大运；比较的是方法卡，不是人生故事。
3. 每模型每例跑三次，记录模型版本、参数、提示词及事实包SHA-256、日期和原输出。不要悄悄换提示词后只保留最好的一次。
4. 要求模型先给analysis_card，至少含four_pillars、selected_pattern、method_labels、favorable、unfavorable、three_lines、main_percent、report_mode、conditional_judgments（无条件性判断时填空数组）。倾向有两读时提供score.py账本与重放结果。
5. 把记录写成JSON数组，字段为model、case_id、repeat、analysis_card，另存参数及哈希。文件放仓库外；若加入自己真人的例更不能传入公用评测数据。
6. 运行 `python evals/evaluate.py --runs /outside/repository/runs.json`。比较器只校验结构化字段与已核对标签，输出硬错误、方法符合度和两两字段一致率；文风和伦理按rubric另行人工审核。
7. 检查“同模型三次”“不同模型”分歧分别在哪里。先修具体不明确的规则或提示，不通过更改答案把所有模型变成“正确”。人工标签有争议就退出自动计分，先请维护者核定。

两种读法的分数是规则内倾向，不是经过验证的人生预测概率。原著案例只提供方法标签，不能证明现实事件可预测。

润下例DTS-XX-01已按用户确认纳入方法评分：conditional_judgments须记录`{"condition":"原局无食伤","element":"火","judgment":"不利","scope":"本例"}`。只写“润下”而漏掉条件不能通过；把火运不利扩写为“全部润下盘”也不能通过。字段用于标准化比对，报告正文仍用自然语言说明；散文中的错误推广另按rubric人工检查。

历法算法抽样对比可单独复现：`python evals/compare_eot.py`、`python evals/compare_jieqi.py`。只输出汇总，不包含私人生日；两算法差值不是绝对正确性的证明。

用户已确认的标签释义：`condition: 原局无食伤`是固定评测简称，指本例“未形成有效食伤泄化”，不是没有食伤字；程序事实亥中甲伤官必须保留。原句为“原局無食傷之化”。输出标签值保持不变，报告正文须写清功能条件，不能由此推广全部润下忌火。
